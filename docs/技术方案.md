## 2. 总体架构

```
┌─────────────────────────────────────────────┐
│  前端 Vue3 SPA（frontend/）                    │
│  Element Plus + TailwindCSS + ECharts        │
└──────────────────┬──────────────────────────┘
                   │ HTTPS / JSON（JWT）
┌──────────────────▼──────────────────────────┐
│  后端 FastAPI（backend/app/）                  │
│  ┌─────────────┐  ┌───────────┐  ┌────────┐  │
│  │ API 路由层    │  │ 业务服务层 │  │ 规则引擎 │  │
│  └─────────────┘  └───────────┘  └────────┘  │
│  ┌─────────────┐  ┌───────────┐              │
│  │ RBAC 鉴权    │  │ 审计日志  │              │
│  └─────────────┘  └───────────┘              │
└───────┬──────────────────────┬──────────────┘
        │                      │
┌───────▼───────┐      ┌───────▼───────┐
│  MySQL 8      │      │ Redis          │
│  业务库        │      │ Celery broker  │
└───────────────┘      └───────────────┘
```

**分层约定：**

- `api/`：路由定义、请求/响应 Schema（Pydantic），不做业务逻辑。
- `services/`：业务逻辑（核保评估、结论生效、状态流转）。
- `models/`：SQLAlchemy ORM 模型，与表一一对应。
- `core/`：鉴权、权限、审计、配置。
- 智能核保评估为纯内存规则计算，走 Celery 异步执行，结果回写申请单。

```

product 1─n application
product 1─n disclosure_question
```

## 4. API 设计（REST，前缀 `/api/v1`）

| --- | --- | --- |

## 5. 核心流程设计

### 5.1 智能核保评估

1. 客户提交申请 → 事务内保存申请/答卷/病史 → 申请单置 `AUTO_UNDERWRITING` → 投递 Celery 任务。
2. 规则引擎按严重度（DECLINE > POSTPONE > EXCLUSION > EXTRA > STANDARD）评估：
   - 遍历启用规则，`condition_json` 命中问卷风险题/病史关键词/家族关键词/年龄/保额 → 触发动作。
   - 动作 = MANUAL → 置 `MANUAL_REQUIRED`；EXAM → 置 `EXAM_REQUIRED`；其余 → 自动写入 `underwriting_result(source=AUTO, is_final=1)`，置 `DECIDED`。
3. 全程写 `audit_log`。

### 5.2 人工核保与复核

核保员出结论（`underwriting_result(source=MANUAL, review_status=PENDING)`）→ 申请单 `REVIEWING` → 主管通过：`review_status=APPROVED, is_final=1`，申请单 `DECIDED`；退回：`review_status=RETURNED`，申请单回 `MANUAL_REQUIRED`，原结论作废（不删，留痕）。

### 5.3 复议

客户发起（校验：申请单 `DECIDED`、30 天内、无已存在复议）→ 申请单 `RECONSIDERING` → 主管处理（维持/变更，写新结论 `source=RECONSIDER, is_final=1`）→ 申请单 `RECONSIDERED`。

### 5.4 体检闭环

创建体检单（`EXAM_REQUIRED`，锁定申请单不再评估）→ 机构录入结果 → 申请单回到 `AUTO_UNDERWRITING` 重新触发评估（携体检数据供规则/人工参考）。

## 6. 权限实现

- JWT payload 含 `user_id`、`role`、`exam_center_id`。
- FastAPI 依赖注入 `CurrentUser`，按路由声明所需角色（如 `require_roles("underwriter", "supervisor")`）。
- 数据范围在 service 层过滤：客户强制 `customer_id=自己`；体检机构强制 `center_id=本机构`。
- 前端根据 `/auth/me` 返回的角色渲染菜单，仅作展示控制，鉴权以后端为准。

## 10. 开发里程碑（建议顺序）

1. **M1 基础框架**：后端骨架、鉴权、RBAC、用户初始化脚本；前端脚手架、登录页。
2. **M2 投保与问卷**：险种/题目配置、投保申请、我的申请。
3. **M3 智能核保**：规则引擎、Celery 任务、自动结论。
4. **M4 人工核保与复核**：待办、案件详情、结论、复核。
5. **M5 体检管理**：体检单、机构录入。
6. **M6 复议 + 结论查询**。
7. **M7 统计看板 + 导出**。

每里程碑完成后更新 `docs/开发进度.md` 并跑一轮测试记入 `docs/测试报告.md`。
